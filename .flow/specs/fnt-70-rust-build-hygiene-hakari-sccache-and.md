# fnt-70-rust-build-hygiene-hakari-sccache-and Rust build hygiene: hakari, sccache and target sweeps

## Goal & Context

Cargo never deletes old build output. Every change of features, profile or flags writes new hashed copies, and the old ones stay. In ai-pet, `rust/target` reached 42 GB (2026-11-08) after it had filled the disk that morning, and each worktree keeps its own target: `../ai-pet-waves/task-*` and `.claude/worktrees/*`. The owner asked for the same hygiene flow-next-tracker is getting as FNT-68: one feature set for every build (cargo-hakari), a shared compiler cache for dependencies (sccache), and a sweep of stale output after each gate (cargo-sweep), measured before and after.

## Architecture & Data Models

- **One feature set.** A committed `workspace-hack` crate generated by cargo-hakari makes every build (`-p`, the whole workspace, clippy, tests, any feature combination such as `aipet --features demo`) resolve dependencies with the same features, so a dependency compiles once per profile instead of once per combination. Every worktree gets it through git.
- **A compiler cache across worktrees.** sccache as `RUSTC_WRAPPER`, with a local disk cache and a size cap. Dependencies from crates.io live at the same path in `~/.cargo/registry` for every worktree, so with one feature set they hit the cache in a second worktree. Workspace crates mostly miss (different paths, incremental builds); that's expected.
- **Sweeps.** After a gate (the local check before a commit, a wave's end), `cargo sweep` removes output not used recently (`--time N`) or not built by the installed toolchain (`--installed`), only when no cargo process is running in that checkout.
- **Separate target directories stay.** One `CARGO_TARGET_DIR` shared by worktrees would serialise builds on cargo's build lock and make branches overwrite each other.

## API Contracts

- `rust/workspace-hack/` (the generated crate) and `rust/.config/hakari.toml`; each workspace crate depends on `workspace-hack`.
- `cargo hakari verify` and `cargo hakari generate --diff` run in CI (`ci.yml`) and the local checks, failing when the hack crate is stale.
- `scripts/build-env.sh` (sourced, opt-in): sets `RUSTC_WRAPPER=sccache` with `SCCACHE_CACHE_SIZE` when sccache is installed, and says so; nothing in the repo requires sccache.
- `scripts/sweep.sh [checkout]`: refuses while a `cargo` or `rustc` process has that checkout as its working directory, else runs `cargo sweep --time <days>` (default 7) and `--installed` in `rust/`, printing the space freed.

## Edge Cases & Constraints

- CI on GitHub Actions: the hakari check is cheap; don't add sccache to CI (no persistent cache there), and keep run counts down (the owner's minutes are limited, although the public repo's standard runners are free).
- Windows (Git Bash, no PowerShell): the scripts run under Git Bash; sccache and cargo-sweep install the same way.
- A sweep must never run during a build in that checkout, and never touch another worktree's target unless asked.
- `cargo hakari` must not change what any shipped binary contains in a way that matters: check the release binary's size and that the pet still runs.

## Acceptance Criteria

- **R1:** A committed `workspace-hack` crate gives every build one feature set, and CI and the local checks fail when it's stale. Errors: a new dependency or feature without regenerating fails `cargo hakari verify` with its message.
- **R2:** With the opt-in build environment, sccache caches dependency compiles across worktrees with a size cap; a second worktree's clean build shows the hit rate. Errors: no sccache installed means plain cargo, with one line saying so.
- **R3:** A sweep script removes stale target output after a gate, and refuses while cargo runs in that checkout. Errors: a running build means "not sweeping: cargo is running in <checkout>", exit 1.
- **R4:** Before-and-after measurements are recorded: target size, duplicate copies of the most duplicated crates, a clean build's time, and the sccache hit rate in a second worktree. Errors: no error surface beyond the measurement.

## Boundaries

No shared `CARGO_TARGET_DIR` across worktrees; no sccache in CI; no remote cache; no change to the release profile.

## Decision Context

Matches flow-next-tracker's FNT-68 so both repositories keep their targets the same way. A shared target directory was rejected for the build lock and branch overwrites. Remote caches are out of scope for one developer's machines.
